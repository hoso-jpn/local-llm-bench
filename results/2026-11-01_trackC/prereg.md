# 事前登録：トラックC（多ターン）

**計測を始める前にこのファイルをコミットする。**

## 目的

コーディングエージェントのように、同じ会話を何ターンも続ける使い方での待ち時間を比べる。1ターン目に長い資料を読ませ、2・3ターン目で追加の質問をする。2ターン目以降に、前のやり取りを読み直さずに済むか（prefix の使い回し）が効く。

## 条件

- エンジンと構成：トラックB と同じ出荷状態（FreeToken v0.2.0＋NVFP4、`--cache-type radix --enable-cache-report`。Strata v0.1.42＋IQ3_S、出荷時の設定）
- 会話：1ターン目は先頭に乱数を付けた資料（コード・日本語、4K / 16K / 30K）＋要約の指示。2・3ターン目は、直前の回答を履歴に積み、「続けて、改善点を3つ挙げてください。」を足す。乱数は会話ごとに変えるので、会話をまたいだ使い回しは起きない
- 出力 256 トークン、捨て1会話＋本計測3会話。各エンジン1セッション（FreeToken → Strata）
- 記録：各ターンの TTFT、`cached_tokens`（返す場合）、Strata はエンジンのログの「reused」

## 予想

| 入力長 | FreeToken 1ターン目 → 2ターン目の TTFT | Strata 1ターン目 → 2ターン目の TTFT |
| --- | --- | --- |
| 4K | 2.9 s → 0.3〜1 s | 1.2 s → 0.3〜1.2 s |
| 16K | 8 s → 0.3〜1 s | 2.9 s → 0.3〜3 s |
| 30K | 11〜16 s → 0.3〜1.5 s | 5 s → 0.3〜5 s |

1. **FreeToken は2ターン目以降、ほぼ全体を使い回す**（`cached_tokens` が直前の会話の長さに近い）。TTFT は入力長によらず 1 秒前後になる
2. **Strata は使い回しの有無がまだ分からない**。公式資料（v1）には「会話のキャッシュはなく、毎回プロンプト全体を処理する」とある一方、セットアップの案内には `--conversation-cache-mib`（複数の会話を保持する）があり、ログには「reused」の欄がある。1つの会話だけなら既定でも使い回すと予想する（予想の幅が広いのはそのため）
3. **使い回しが効くなら、2ターン目以降の TTFT の差は縮むか逆転する**。1ターン目の差（トラックB で約2〜3倍）は、会話の最初だけの問題になる

## 結果（2026-11-01 計測）

各エンジン1セッション、本計測3会話の中央値。エラー 0。「使い回し」は FreeToken が返す `cached_tokens`、Strata が返す `timings.cache_n`（エンジンのログの「reused」と一致）。

| 種類 | 入力長 | FreeToken TTFT（1 → 2 → 3ターン目） | 使い回したトークン（2・3ターン目） | Strata TTFT（1 → 2 → 3ターン目） | 使い回したトークン（2・3ターン目） |
| --- | --- | --- | --- | --- | --- |
| コード | 4K | 2.93 → 2.47 → 2.46 s | 4,096 / 4,416 | 1.17 → 0.24 → 0.11 s | 4,152 / 4,686 |
| コード | 16K | 8.19 → 8.25 → 2.48 s | 0 / 16,704 | 2.88 → 0.11 → 0.24 s | 16,696 / 16,716 |
| コード | 30K | 10.79 → 2.49 → 2.48 s | 30,720 / 31,040 | 4.95 → 0.25 → 0.26 s | 30,769 / 31,050 |
| 日本語 | 4K | 3.31 → 2.46 → 2.46 s | 4,160 / 4,416 | 1.17 → 0.10 → 0.10 s | 4,422 / 4,700 |
| 日本語 | 16K | 10.48 → 2.46 → 2.47 s | 16,448 / 16,704 | 2.77 → 0.10 → 0.11 s | 16,711 / 16,988 |
| 日本語 | 30K | 15.94 → 2.48 → 2.48 s | 30,784 / 31,040 | 4.91 → 0.10 → 0.11 s | 31,046 / 31,322 |

- **両エンジンとも、2ターン目以降はほぼ全体を使い回した。** Strata にも既定で会話の使い回しがある（1つの会話なら）。公式資料（v1）の「会話のキャッシュはない」という記述は、v0.1.42 では古くなっている
- **Strata の2ターン目以降の TTFT は 0.1〜0.26 秒。** 新しく読むのは追加分の約 20〜300 トークンだけ
- **FreeToken は使い回しても、TTFT が約 2.46 秒より下がらない。** 入力長にもほぼ関係しない。トラックB の 1K の TTFT（2.54 秒）とも一致し、NVFP4 の構成には「リクエストごとに約 2.4 秒かかる下限」がある
- 例外：FreeToken のコード 16K の2ターン目は、中央値で使い回しが 0 だった（8.25 秒）。原因は未確認（radix キャッシュの追い出しの可能性）

### FreeToken の「約 2.4 秒の下限」の仮説

prefill では、新しいトークンが数十〜数百個でも、各層で多くの expert に振り分けられ、全体としてほとんどの expert が呼ばれる。NVFP4 では VRAM に置けるのが全 24,576 個の約 24%（5,926 スロット）なので、残り約 76% を PCIe で運ぶ必要がある。

- 運ぶ量の概算：24,576 × 0.76 × 約 2.64 MiB ≒ 約 52 GB
- PCIe 5.0 x8 の実測 28.9 GB/s で割ると約 1.8 秒。これに計算などが加わって約 2.4 秒

つまり、**キャッシュにない expert を全部 PCIe で運ぶ1往復**が、どんなに短い prefill にもかかる。Strata は、小さな prefill のチャンクでは、キャッシュにない expert を CPU でその場で計算するため、この往復が起きない。この仮説が正しければ、PCIe を x16 に戻すと下限は約半分になり、GGUF（VRAM に約 54% を置ける）では下限が小さくなる（トラックA の 1K で 1.56 秒）。`--moe-collect-stats` と PCIe の記録（`gpu.csv`）で確かめられる。

### 記事への影響

コーディングエージェントのように同じ会話を続ける使い方では、待ち時間の差がいちばん大きく出る。Strata は2ターン目以降ほぼ待ち時間がなく、FreeToken＋NVFP4 は毎ターン約 2.5 秒待つ。この差は、prefix の使い回しの有無ではなく、「小さな prefill でもキャッシュにない expert を全部運ぶかどうか」という作りの違いから来ている（仮説）。
